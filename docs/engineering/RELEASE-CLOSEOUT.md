## Remaining release sequence

1. Inspect final candidate CI and native conformance, including step outcomes and artifact/source pins.
2. Record human technical delta review of the final source and configuration. A prior review of older commits is retained as history, not substituted.
3. Merge reviewed changes through existing branch controls; do not force-update protected `main`.
4. Verify exact post-merge main CI and the pinned Halibut integration against the resulting SWOOSH commit. A passing branch run is not a passing main run.
5. For Halibut, apply its prepared main ruleset, then complete the owner-approved visibility change only after the existing release gates are satisfied.
6. Run `Publish verified preview` on `main`, supplying the reviewed merged PR number. The workflow performs the tag/release operation only after validating its gates.

The current connector exposes code/PR operations but no repository administration, visibility mutation or release-creation endpoint. The ruleset and release workflow make those operations concrete; they are not claimed applied merely because their files exist. Human approval and legal signatures cannot be generated by this implementation.

The existing `RELEASE_CHECKLIST.md` remains the release authority. This file adds evidence-producing controls; it does not remove its human technical-review requirement.
